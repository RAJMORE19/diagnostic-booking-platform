STEP 15 — Create Dockerfile

Open:

```bash
nano Dockerfile
```

Use:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY app.py .

RUN useradd --create-home appuser

USER appuser

EXPOSE 8000

CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]
```

Important production decisions

We are already practicing:

Slim base image

No Python bytecode

Unbuffered logs

Non-root user

Explicit port

No unnecessary packages

Later we will improve this with a multi-stage build where it provides a real benefit.

DAY 1 — INTERVIEW QUESTIONS FROM THIS STEP

Q1. Why did you create /health and /ready separately?

Interview answer:

> I separated liveness and readiness because they solve different problems. Liveness tells Kubernetes whether the application process is alive, while readiness tells Kubernetes whether the application is ready to receive traffic. For example, if my application starts but PostgreSQL is unavailable, I may want the pod to remain alive but not receive production traffic.

---

Q2. Why are you running the container as a non-root user?

> Running as a non-root user reduces the impact of container compromise. If an attacker gains access to the application process, they don't automatically have root privileges inside the container. It's one of the basic container-hardening practices I apply before deploying workloads to Kubernetes.

---

Q3. Why use Docker if Kubernetes will eventually run the application?

> Kubernetes orchestrates containers; it doesn't replace the container image itself. Docker gives us a reproducible application artifact that can run locally, in CI, and eventually in EKS. Jenkins can build the image, Trivy can scan it, ECR can store it, and Kubernetes can pull and run the same image.

---

Q4. What happens when you run docker run?

A good 3-year-level answer:

> Docker creates a container from the specified image, creates the container's isolated filesystem and networking context, starts the configured process, and maps the host port to the container port. In my case, traffic to host port 8000 is forwarded to Uvicorn listening on port 8000 inside the container.
