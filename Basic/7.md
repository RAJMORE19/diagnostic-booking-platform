# 1. TERRAFORM REMOTE STATE

This is one of the **most important Day 7 topics**.

Instead of:

```text
Developer Laptop
      ↓
terraform.tfstate
```

use:

```text
                    S3
                     │
              Terraform State
                     │
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
   Developer 1   Developer 2    CI/CD
```

Benefits:

* Centralized state
* Team collaboration
* State persistence
* Better recovery
* CI/CD compatibility
* Controlled access

---

# 2. S3 BACKEND

Your Terraform backend stores state remotely.

Conceptually:

```text
terraform.tfstate
       ↓
      S3
```

Example:

```hcl
terraform {
  backend "s3" {
    bucket = "blood-test-terraform-state"
    key    = "dev/terraform.tfstate"
    region = "ap-south-1"
  }
}
```

Don't blindly copy this into your project—bucket names and backend configuration should match your actual AWS setup.

---

# 3. STATE LOCKING

Why locking?

Imagine:

```text
Developer A
terraform apply
      │
      ↓
    State
```

At exactly the same time:

```text
Developer B
terraform apply
      │
      ↓
    State
```

This can cause conflicts.

So you need state locking.

Understand:

```text
Terraform
   ↓
Lock State
   ↓
Modify Infrastructure
   ↓
Update State
   ↓
Unlock
```

For AWS, learn both:

* S3-based remote state
* Modern S3-native locking capabilities
* DynamoDB-based locking as the traditional AWS Terraform pattern

**Interview point:** Don't say DynamoDB is the only way to lock Terraform state.

---

# 4. TERRAFORM STATE SECURITY

Terraform state can contain sensitive infrastructure information and sometimes sensitive values.

Therefore:

```text
S3 Bucket
   ↓
Private
   ↓
Encryption
   ↓
IAM-controlled access
```

Never make your Terraform state bucket public.

---

# 5. STATE VERSIONING

Enable S3 versioning.

Why?

Suppose:

```text
terraform.tfstate
```

gets accidentally modified or corrupted.

Versioning gives you previous versions.

Concept:

```text
State v1
State v2
State v3
State v4
```

This improves recovery.

# 6. TERRAFORM MODULES

Day 6 introduced modules.

Today you need to actually understand how to design them.

Example:

```text
modules/
│
├── vpc/
├── iam/
├── ecr/
├── rds/
├── ec2/
├── alb/
└── monitoring/
```

Each module should have:

```text
main.tf
variables.tf
outputs.tf
```

Example:

```text
modules/vpc/
│
├── main.tf
├── variables.tf
└── outputs.tf
```

---

# 7. MODULE INPUT → MODULE OUTPUT

Think:

```text
Environment
     │
     ↓
VPC Module
     │
     ├── Input
     │
     └── Output
             ↓
          VPC ID
             ↓
        EC2 Module
```

Example:

```hcl
module "vpc" {
  source = "../../modules/vpc"

  project_name = "blood-test"
  environment  = "dev"
}
```

Then:

```hcl
module "ec2" {
  source = "../../modules/ec2"

  vpc_id = module.vpc.vpc_id
}
```

This is **module composition**.

---

# 8. MODULE REUSABILITY

Without modules:

```text
dev/main.tf
staging/main.tf
prod/main.tf
```

could become duplicated and difficult to maintain.

With modules:

```text
              VPC MODULE
             /     |     \
            /      |      \
          DEV   STAGING    PROD
```

Same reusable logic.

Different configuration.

# 11. VARIABLES

Use variables for environment-specific configuration.

Example:

```hcl
variable "instance_type" {
  type = string
}
```

DEV:

```text
instance_type = smaller-size
```

PROD:

```text
instance_type = production-size
```

The exact instance types should be selected based on workload and AWS availability/cost requirements.

# 12. LOCALS

Use locals for naming and common configuration.

Example:

```hcl
locals {
  name_prefix = "${var.project_name}-${var.environment}"
}
```

Then:

```text
blood-test-dev-vpc
blood-test-dev-rds
blood-test-dev-alb
```

and:

```text
blood-test-prod-vpc
blood-test-prod-rds
blood-test-prod-alb
```

# 13. OUTPUTS

Modules should expose only useful information.

Example:

```hcl
output "vpc_id" {
  value = aws_vpc.main.id
}
```

Another module can consume it:

```hcl
vpc_id = module.vpc.vpc_id
```

Important principle:

> **Don't hardcode resource IDs when Terraform can establish the relationship dynamically.**

# 15. TERRAFORM DEPENDENCIES

Terraform automatically creates a dependency graph.

Example:

```text
VPC
 ↓
Subnet
 ↓
EC2
```

and:

```text
ALB
 ↓
Target Group
 ↓
EC2
```

Terraform determines the correct creation order based on references.

---

# 16. IMPLICIT DEPENDENCY

Example:

```hcl
subnet_id = module.vpc.private_subnet_id
```

Terraform understands:

```text
EC2 depends on VPC module
```

This is an implicit dependency.

---

# 17. EXPLICIT DEPENDENCY

Sometimes you may need:

```hcl
depends_on = [
  aws_iam_role_policy.example
]
```

Use `depends_on` only when Terraform cannot infer the dependency automatically.

**Interview answer:**

> I prefer implicit dependencies through resource references because they're clearer and more maintainable. I use `depends_on` only for dependencies Terraform cannot infer.

---

# 18. TERRAFORM DRIFT

Very important production scenario.

Terraform created:

```text
EC2
```

Then someone manually changes the instance configuration in AWS Console.

Now:

```text
Terraform Code
      ≠
AWS Infrastructure
```

This is **configuration drift**.

Run:

```bash
terraform plan
```

Terraform detects differences.

Concept:

```text
Terraform Code
      ↓
Terraform Plan
      ↓
Compare
      ↑
AWS Infrastructure
```

---

# 19. HOW TO HANDLE DRIFT

Don't immediately destroy everything.

First:

```bash
terraform plan
```

Understand:

```text
What changed?
Why?
Was it intentional?
```

Then decide:

```text
Keep manual change
       OR
Revert through Terraform
       OR
Update Terraform code
```

Production principle:

> **Terraform should remain the source of truth for Terraform-managed infrastructure.**

# 20. TERRAFORM IMPORT

What if an AWS resource already exists?

Example:

```text
Existing VPC
```

but Terraform doesn't manage it.

You can bring it under Terraform management using import functionality.

Concept:

```text
Existing AWS Resource
        ↓
Terraform Import
        ↓
Terraform State
```

Important:

> Importing a resource into state doesn't automatically write a complete Terraform configuration for that resource. You still need correct configuration/code.

---

# 21. TERRAFORM WORKSPACES

Understand Terraform Workspaces.

They can maintain multiple state instances for the same configuration.

Concept:

```text
Workspace
│
├── dev
├── staging
└── prod
```

But for your production-grade project, don't automatically choose workspaces just because they exist.

A common approach is:

```text
environments/
├── dev/
├── staging/
└── prod/
```

with separate state.

Know the trade-off.

### Interview question:

**Workspace vs separate environment directories?**

Good answer:

> Workspaces can separate state for similar configurations, but for larger production environments I prefer explicit environment directories or separate root modules because they make configuration, variables, state and deployment boundaries clearer.

# 22. TERRAFORM SENSITIVE VARIABLES

Example:

```hcl
variable "db_password" {
  sensitive = true
}
```

But remember:

```text
sensitive = true
```

does **not magically remove the secret from Terraform state**.

For production:

```text
Secrets Manager
      ↓
Application
```

is preferable for application secrets.

---

# 23. AWS CREDENTIALS FOR TERRAFORM

Don't do this:

```hcl
provider "aws" {
  access_key = "..."
  secret_key = "..."
}
```

Instead use secure AWS authentication mechanisms such as:

```text
Local Developer
      ↓
AWS CLI / IAM Identity Center / Role
      ↓
AWS

CI/CD
      ↓
OIDC / IAM Role
      ↓
AWS
```

For GitHub Actions, **OIDC + IAM Role** is a key production pattern.

# 27. TERRAFORM PLAN IN CI

This is particularly valuable.

Pull Request:

```text
Terraform Code Change
       ↓
GitHub Actions
       ↓
terraform plan
       ↓
Review Infrastructure Changes
```

Example:

```text
Plan:

+ create aws_security_group.example
~ modify aws_instance.app
- destroy aws_xxx.old
```

The team can review the impact **before applying it**.
